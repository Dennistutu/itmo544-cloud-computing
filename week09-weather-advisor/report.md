## Answer 1: What Moto could not prove and which integration tests covered the gaps

Moto stores settings and rules as data, but it does not run real servers, send real network traffic, or evaluate IAM policies. Because of that, it could not prove that the database had no real automated backups, that the security group rules actually blocked and allowed traffic, that PostgreSQL used TLS with certificate verification, or that IAM permissions really allowed and denied access as expected. It also could not prove that EC2 instances would boot, applications would run, Gemini would return answers, or how long recovery would take. The integration test test_database_is_private_single_az_encrypted_and_unbacked confirmed that the real database had zero backup retention and no snapshots, and AWS itself reported that no automated backup existed. The network tests test_app_instances_are_reachable_only_through_the_alb and test_database_port_is_not_reachable_from_this_computer checked that app instances could only be reached through the load balancer and that the database port was not reachable from my computer. The cache and /history tests confirmed that the application connected to RDS using verified TLS, because the cache only works when that connection succeeds. The IAM test used AWS’s policy simulator to check that each role could access only its own secret. The nine smoke tests and the health test confirmed that the real application worked and received a source=gemini answer. Finally, the two chaos tests checked real failure and recovery: the forecast kept working with cache: unavailable when the database was cut off, the advisor returned a fast 502 within two seconds when the weather tier failed, and the weather tier recovered in 87 seconds.

## Answer 2: Python vs. Bash for creating the database and waiting

Python made the database creation process easier to get right because it handled specific errors instead of hiding every error like Bash’s 2>/dev/null || true. It used a dictionary for the database settings and a clear waiter configuration, and it passed the password only at the moment of the AWS request without ever logging it. During this lab, Python also reported the exact DBInstanceAutomatedBackupNotFound error, which showed right away that the test needed fixing rather than the database stack. Python was also easier to test because db_instance_request() is a pure function, so I could check settings such as the database class, zero backup retention, private access and encryption without connecting to AWS. I could also test the whole create-and-delete process with Moto in seconds without paying for AWS resources, while testing the Bash version would require running it against real AWS and paying for the database.
